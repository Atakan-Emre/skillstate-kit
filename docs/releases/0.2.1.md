# 0.2.1 — task integrity hardening

Task-profile progress must pass through the checkpoint lifecycle. Generic update
and operation-reservation calls can manage blockers but cannot replace completed
steps, milestones, artifact references or the task goal. This closes a validation
bypass in 0.2.0's project API. Domain-specific semantic updates remain supported.

Completion now also rejects empty evidence, inconsistent artifact indexes,
duplicate/out-of-order milestones and mismatched resource fingerprints. The
database schema remains version 1; existing valid records need no migration.

Lifecycle instructions use returned state snapshots instead of requesting context
after every mutation, and distinguish historical inspection evidence from files
whose changes invalidate a milestone. These are behavioral refinements, not a
new measured token-savings claim.

README and PyPI documentation describe the product, installation and contracts
without development-session narratives. A research-alignment document identifies
the managed-runtime boundary and native-host limitations. Internal planning
documents are excluded from source distributions.

Development pytest and package installation tooling were updated following
dependency advisories. Release CI now audits the locked dependency snapshot.
Dependency scans report known findings at the scan time, not universal security.

Validation includes task guard bypass attempts over the service and real MCP,
corrupted milestone records, fresh-runtime observation isolation, existing
smolagents evidence verification, old-store compatibility and clean-package tests.
No new live Claude Code acceptance or performance experiment is claimed.
